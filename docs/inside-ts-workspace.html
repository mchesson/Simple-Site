Inside TS Workspace

The backend, the assistant, and the glass box that shows you what both of them actually did.

Postgres 16 · Node 22 · claude-opus-5 23 tools · 26 tables · 52 tests

Until now the workspace was one page that kept its data in the page. That was enough to argue about the shape of the business, and not enough to run it. This is the machinery underneath: a database that refuses to hold a state the business does not allow, an assistant that is genuinely Claude with its hands on that data, and an inspector that answers the question you asked for — how does it work, and what is it doing right now.

Three things run. A Postgres database holding accounts, sites, people, projects, paperwork and money. A Node server that owns every write and records everything it does. And Claude, reached over the API, given tools onto that database rather than a copy of it.

The part worth being precise about: the model does not hold your data. Nothing is loaded into it and nothing is remembered by it between questions. Each turn, it is handed a set of tools; it decides which to call; the server runs them against Postgres and hands back rows. That is why the answers can be current, and why the inspector can show you the exact statement behind any figure.

The assistant

Why it can answer in plain English

Twenty-three tools cover accounts, sites, contacts, projects, activity, documents, pipelines and PO burn-down. Most are ordinary: fetch this, list those, write that. Three design choices do the heavy lifting.

A tool that cannot proceed says what it needs

Ask it to add a hiring manager and give it only a name, and the tool does not fail — it returns the gap.

{ "error": "missing_information",
  "needs": [
    "the company they work for (a manager sits on an account)"
  ],
  "hint": "Ask the user for these before calling again." }

The model reads that and asks you for exactly that one thing. This is what makes entering a record by conversation feel like a conversation instead of a form rejecting you.

A name that matches two things is a question, not a guess

"Globex" when there is a Globex Manufacturing and a Globex Logistics returns both and asks which. Guessing here means logging a call against the wrong company, which is worse than a moment's friction.

When no tool fits, it writes SQL

Ranked lists, aggregates, questions that span four entities — no purpose-built tool can anticipate them all. So the model can write a SELECT, and it reads the live schema from the database first so what it is told cannot drift from what is there. The safety is not a promise:

-- on the connection the assistant's queries travel
insert into app_user (email, full_name) values ('x@y.z','X');
ERROR:  permission denied for table app_user

That is Postgres refusing, on a role that was granted SELECT and nothing else. Pattern checks sit in front of it as a courtesy to the model, so it gets a clear error instead of a permissions failure halfway through — but they are not what is protecting you.

Data plane

The rules live in the database

An application check is a rule that holds until someone writes a second code path. A constraint is a rule that holds. These are the ones the business actually turns on, and each has a test asserting it, because a constraint nobody tested is a comment.

The ruleEnforced byWhat it prevents
A manager sits on an accountcheck Contacts nobody can route a req through
Everyone is a manager, a candidate, or bothcheck Records with no reason to exist
A document belongs to exactly one thingcheck An MSA that is also somehow a resume
A project uses its own account's sitestrigger Work booked to the wrong plant
Two rates of a type never overlap in timeexclusion Silent double-billing and broken history
Owners are workspace usersforeign key Commission owed to a name someone typed

The last of the checks is the one worth showing, because most systems get it wrong by storing a single rate column and editing it:

create table placement_rate (
  placement_id   uuid not null references placement(id),
  rate_type      text not null,
  pay_rate       numeric(12,4) not null,
  bill_rate      numeric(12,4) not null,
  burden_pct     numeric(6,4)  not null default 0,
  effective_from date not null,
  effective_to   date,
  validity       daterange generated always as
                 (daterange(effective_from, effective_to, '[)'))
                 stored,
  supersedes_id  uuid references placement_rate(id),

  -- the whole point
  exclude using gist (placement_id with =,
                       rate_type    with =,
                       validity     with &&)
);

A rate is never edited. A change writes a new row that starts where the last one ended, and the exclusion constraint makes an overlap impossible rather than unlikely. An invoice from March still reconciles against the rate that was in force in March.

Nothing is destroyed anywhere. Every update writes the previous version to record_revision before the row changes, inside the same transaction. Deletes are an archived_at stamp — the row stays. Ask the assistant what a record looked like before and it can tell you, because the answer is stored rather than reconstructed.
Money

Margin, defined once

Burden is a percentage of pay, not of bill. Every system that gets this backwards overstates margin, and overstates it most where the pay rate is lowest — which is exactly where you can least afford to be wrong. So the formula is a database function and there is only one of it:

gross_margin(pay, bill, burden_pct) = bill − pay − (pay × burden_pct / 100)

Marcus Bell on the Globex plant data platform, with the raise that landed on 1 August:

EffectivePayBillBurden SpreadGross marginGM %
1 Jun – 1 Aug 2026$65.00$105.00 22%$40.00$25.70 24.48%
1 Aug 2026 – open$68.00$108.00 22%$40.00$25.04 23.19%

The spread is $40 in both rows and tells you nothing. The raise passed $3 to the consultant and $3 to the bill rate, which looks like a wash and is not: burden rides on the pay increase, so the cash margin fell 66¢ an hour and the percentage fell more than a point. On a 40-hour week across a year that is about $1,370 — from a change that reads as neutral on a rate sheet.

Purchase order burn-down

You asked for this specifically, and it is in. One view, so every screen in the org reads the same number: what was committed, what approved time has burned, what is submitted and waiting on the client, what is left, and how many days until the PO expires.

POCommittedBurnedAwaiting approval RemainingExpires
PO-GLX-88412$180,000 $46,560 · 25.9%$8,640 $133,44031 Oct · 64 days
PO-GLX-88500$95,000$0 $0$95,000 31 Jan · 156 days

The two middle columns are the ones that earn their place. Burned is approved time only — money you can invoice. Awaiting approval is work already done that the client has not signed off, which is money at risk and invisible in most systems until it becomes an argument. Ask for POs running out in the next 90 days and you get them ranked by how soon, not by how full.

Observability

The inspector

Five sections, at /inspect.html. Nothing in it is a reconstruction — each panel reads the running system.

SectionWhat it showsRead from
Turns Every model call, tool call and SQL statement, with timings, tokens, cost and reasoning. Steps appear live as a turn runs. the trace itself
Data The schema with row counts, and a query console. information_schema
Tools The 23 tool definitions, exactly as sent to the model. the request builder
Prompt The system prompt verbatim, the request settings, the pricing used to cost each turn. the request builder
Events Every change, each linking back to the turn that caused it. domain_event

The query console runs on the same read-only role the assistant uses. If you doubt a number the assistant gave you, you can check it against the database in the same window, by hand, in about fifteen seconds.

Running it

What you need

PostgreSQL 16 and Node 22. The code is on the claude/applicant-tracking-crm-design-tkjh5b branch, under server/.

createdb ts_workspace
psql -d ts_workspace -f src/bootstrap.sql   # as a superuser: creates the two roles
npm install
cp .env.example .env                        # then put your API key in it
npm run db:reset                            # schema + demo data
npm start

Chat needs an ANTHROPIC_API_KEY. Everything else — the database, the record screens, the inspector, the query console — runs without one, and the chat endpoint tells you the key is missing rather than failing quietly.

Honestly

What is proven and what is not

Proven. Fifty-two tests run against a real Postgres database built from the same schema the application uses — a mock would not catch the constraints, and the constraints are where most of the design lives. Every rule in the table above is asserted. So is the read-only role, including a direct write attempt that Postgres refuses. So is the revision history, the role-aware activity logging, the deduplication when you create someone who already exists, PO burn-down arithmetic, the tool loop's iteration cap, and the stability of the cached system prompt.

Not proven. No live call to the Claude API was made. There was no credential in the environment this was built in, so the agent loop was exercised against a scripted stand-in for the API client. The request shape is asserted against the documented parameters — model, adaptive thinking, effort, tool schemas — but the round trip has not been run. Add a key and send one message. If it answers, the loop is good; if it does not, the error will be in the trace.

Still to build. Managed-service deliverables and milestones. Engagements with a team lead over several resources. The bench knowledge base and redeployment. Change orders exist as a table but have no workflow around them yet. Timecard entry and approval is seeded, not built — burn-down reads real timecards, but nobody submits one through the product yet.
