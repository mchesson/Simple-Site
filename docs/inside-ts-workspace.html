Inside TS Workspace

The backend, the assistant, and the glass box that shows you what both of them actually did.

Postgres 16 · Node 22 · claude-opus-5 42 tools · 37 tables · 100 tests

Until now the workspace was one page that kept its data in the page. That was enough to argue about the shape of the business, and not enough to run it. This is the machinery underneath: a database that refuses to hold a state the business does not allow, an assistant that is genuinely Claude with its hands on that data, and an inspector that answers the question you asked for — how does it work, and what is it doing right now.

Three things run. A Postgres database holding accounts, sites, people, projects, paperwork and money. A Node server that owns every write and records everything it does. And Claude, reached over the API, given tools onto that database rather than a copy of it.

The part worth being precise about: the model does not hold your data. Nothing is loaded into it and nothing is remembered by it between questions. Each turn, it is handed a set of tools; it decides which to call; the server runs them against Postgres and hands back rows. That is why the answers can be current, and why the inspector can show you the exact statement behind any figure.

The assistant

Why it can answer in plain English

Forty-two tools cover accounts, sites, contacts, projects, activity, documents, pipelines, timesheets, approvals, unlocks, invoices, PO burn-down and the audit trail. Most are ordinary: fetch this, list those, write that. Three design choices do the heavy lifting.

A tool that cannot proceed says what it needs

Ask it to add a hiring manager and give it only a name, and the tool does not fail — it returns the gap.

{ "error": "missing_information",
  "needs": [
    "the company they work for (a manager sits on an account)"
  ],
  "hint": "Ask the user for these before calling again." }

The model reads that and asks you for exactly that one thing. This is what makes entering a record by conversation feel like a conversation instead of a form rejecting you.

A name that matches two things is a question, not a guess

"Globex" when there is a Globex Manufacturing and a Globex Logistics returns both and asks which. Guessing here means logging a call against the wrong company, which is worse than a moment's friction.

When no tool fits, it writes SQL

Ranked lists, aggregates, questions that span four entities — no purpose-built tool can anticipate them all. So the model can write a SELECT, and it reads the live schema from the database first so what it is told cannot drift from what is there. The safety is not a promise:

-- on the connection the assistant's queries travel
insert into app_user (email, full_name) values ('x@y.z','X');
ERROR:  permission denied for table app_user

That is Postgres refusing, on a role that was granted SELECT and nothing else. Pattern checks sit in front of it as a courtesy to the model, so it gets a clear error instead of a permissions failure halfway through — but they are not what is protecting you.

Data plane

The rules live in the database

An application check is a rule that holds until someone writes a second code path. A constraint is a rule that holds. These are the ones the business actually turns on, and each has a test asserting it, because a constraint nobody tested is a comment.

The ruleEnforced byWhat it prevents
A manager sits on an accountcheck Contacts nobody can route a req through
Everyone is a manager, a candidate, or bothcheck Records with no reason to exist
A document belongs to exactly one thingcheck An MSA that is also somehow a resume
A project uses its own account's sitestrigger Work booked to the wrong plant
Two rates of a type never overlap in timeexclusion Silent double-billing and broken history
Owners are workspace usersforeign key Commission owed to a name someone typed

The last of the checks is the one worth showing, because most systems get it wrong by storing a single rate column and editing it:

create table placement_rate (
  placement_id   uuid not null references placement(id),
  rate_type      text not null,
  pay_rate       numeric(12,4) not null,
  bill_rate      numeric(12,4) not null,
  burden_pct     numeric(6,4)  not null default 0,
  effective_from date not null,
  effective_to   date,
  validity       daterange generated always as
                 (daterange(effective_from, effective_to, '[)'))
                 stored,
  supersedes_id  uuid references placement_rate(id),

  -- the whole point
  exclude using gist (placement_id with =,
                       rate_type    with =,
                       validity     with &&)
);

A rate is never edited. A change writes a new row that starts where the last one ended, and the exclusion constraint makes an overlap impossible rather than unlikely. An invoice from March still reconciles against the rate that was in force in March.

Nothing is destroyed anywhere. Deletes are an archived_at stamp — the row stays. Ask the assistant what a record looked like before and it can tell you, because the answer is stored rather than reconstructed. How it is stored is the next section.
Money

Margin, defined once

Burden is a percentage of pay, not of bill. Every system that gets this backwards overstates margin, and overstates it most where the pay rate is lowest — which is exactly where you can least afford to be wrong. So the formula is a database function and there is only one of it:

gross_margin(pay, bill, burden_pct) = bill − pay − (pay × burden_pct / 100)

Marcus Bell on the Globex plant data platform, with the raise that landed on 1 August:

EffectivePayBillBurden SpreadGross marginGM %
1 Jun – 1 Aug 2026$65.00$105.00 22%$40.00$25.70 24.48%
1 Aug 2026 – open$68.00$108.00 22%$40.00$25.04 23.19%

The spread is $40 in both rows and tells you nothing. The raise passed $3 to the consultant and $3 to the bill rate, which looks like a wash and is not: burden rides on the pay increase, so the cash margin fell 66¢ an hour and the percentage fell more than a point. On a 40-hour week across a year that is about $1,370 — from a change that reads as neutral on a rate sheet.

Money

Time, purchase orders and invoices

What burns a PO, and what only looks like it

A consultant fills in one timesheet a week and allocates their hours day by day across whatever projects and purchase orders they worked on. Approval follows that allocation rather than the week: each client manager approves the part belonging to their project, so one slow approver cannot hold up a week of billing.

And a purchase order is burned by what we have invoiced, not by what our people worked. Those are different numbers, and the gap between them is where the money hides:

So the burn-down carries every stage rather than collapsing them:

PO-GLX-88412AmountWhat it means
Submitted, pending$12,960 Three weeks claimed, waiting on Globex. Not earned.
Approved, unbilled$0 Accepted work we have not billed. Earned revenue in our own queue.
Drafted, not sent$8,640 An invoice prepared but not issued. Still ours, not theirs.
Invoiced$33,600 Billed. This is the burn — 18.7% of the PO.
Paid / outstanding$16,800 / $16,800 Half of it collected, half still owed.
Remaining$146,400 What the PO can still be billed for.
Projected remaining$137,760 What is left once everything in the pipeline is billed.
The failure this exists to catch. A purchase order can read healthy on remaining and already be spent, because a month of approved time is sitting unbilled. When projected remaining goes negative the PO is over-committed before a single invoice has been raised. Asking for POs at risk returns exactly those, not the ones that merely look full.

What the database will not let you do

Entering time:

  • Put more than 24 hours on a day, however it is split across projects.
  • Charge a day that falls outside the week the sheet is for.
  • Charge to a purchase order that belongs to a different project, or to a project the consultant is not placed on — the project is derived from the placement, not taken from whoever is asking.
  • Change or delete a week that has been submitted. The lock is on the allocation; approving still writes the frozen value onto the same rows.
  • Decide the same packet twice. The second attempt names who already decided it.

Billing it:

  • Approval freezes the value at the bill rate in force on each day, read from the effective-dated rate history. A Tuesday worked in March still prices at March's rate in June. Rejection releases it.
  • Only approved days can be invoiced.
  • A day cannot be billed twice on any live invoice.
  • An invoice bills one PO. A day allocated elsewhere is refused, so an invoice for one purchase order can never pick up hours charged to another.
  • A sent invoice is frozen. Lines change only in draft.
  • An invoice cannot overrun its PO. The error names the remedy rather than just failing:
update invoice set status = 'sent' where id = ...;
ERROR:  this invoice would put PO-1 over its limit: 12000.00 committed,
        8400.00 already invoiced, 9200.00 on this invoice.
        Raise a change order or a new PO.

Voiding never deletes. The invoice stays on the record and its weeks become billable again — which is the right behaviour when something was booked to the wrong PO, and the wrong behaviour to discover you do not have at month end.

Governance

Everything leaves a trace

Written by the database, not by the code

Every insert, update and delete on every table lands in one audit log, put there by a trigger on the table itself. That distinction carries the whole guarantee: an application can forget to call the helper that records history, and eventually one code path does. A trigger cannot be forgotten, so a change made by the app, by the assistant, by a migration script or by somebody at a database prompt all leave the same record.

Kept on every changeWhy it earns its place
Before and after The full row on both sides, so "what did this look like" always has an answer.
Fields that changed Reading a diff of two JSON blobs is not a review. The list is.
Acting user Carried in a transaction-local setting the server puts on the connection, so attribution does not depend on the caller remembering to pass it.
Reason Filled in where the action has one. Months later this is the column people actually want.
Transaction id One user action usually touches several tables. This ties them back into a single event.

The log refuses UPDATE and DELETE on itself. Once a line is written it stays, including for whoever administers the database.

Approved time is locked

Once a client manager approves a week, those days are frozen. Not "the screen does not offer it" — nobody can change or delete them, including a direct SQL statement:

update timesheet_entry set hours = 12 where ...;
ERROR:  that time was approved and is locked — an admin has to unlock it first

The lock sits on the approval packet rather than the week, and that is not a detail. Before it did, one manager rejecting their project reopened the whole week — including days another manager had already approved, frozen, and possibly invoiced. A corrected week now replaces only the part that came back.

Getting locked time open again is deliberate, and every step is on the record:

  1. Someone raises an unlock request with a reason. Only one can be open on a week at a time.
  2. An admin grants or denies it. The database checks the role, and refuses a self-grant — whoever asked cannot be the one who approves it.
  3. Granting is refused outright if the time is already on a live invoice. Void or credit the invoice first, rather than leave an invoice standing against time that no longer exists.
  4. A grant is a key with a life: it expires in a day, and is spent on first use. Re-approving and reopening again needs a fresh one.

The inspector

Five sections, at /inspect.html. Nothing in it is a reconstruction — each panel reads the running system.

SectionWhat it showsRead from

The query console runs on the same read-only role the assistant uses. If you doubt a number the assistant gave you, you can check it against the database in the same window, by hand, in about fifteen seconds.

Running it

What you need

PostgreSQL 16 and Node 22. The code is on the claude/applicant-tracking-crm-design-tkjh5b branch, under server/. One command:

./setup.sh

That installs dependencies, creates the database and its two roles, builds the schema, seeds demo data and starts the server. If psql on your machine is not a superuser, point it at one:

TS_SUPERUSER_PSQL="sudo -u postgres psql" ./setup.sh

Chat needs an ANTHROPIC_API_KEY. Everything else — the database, the record screens, the inspector, the query console — runs without one, and the chat endpoint tells you the key is missing rather than failing quietly.

Honestly

What is proven and what is not

Proven. One hundred tests run against a real Postgres database built from the same schema the application uses — a mock would not catch the constraints, and the constraints are where most of the design lives. Every rule in the table above is asserted. So is the read-only role, including a direct write attempt that Postgres refuses. So is the revision history, the role-aware activity logging, the deduplication when you create someone who already exists, the tool loop's iteration cap, and the stability of the cached system prompt. The time and money path gets the most attention: a day split across two projects, the day and week limits, a purchase order from the wrong project, a locked week, partial approval, rejection releasing value, a week reopening for correction, a project with no approver on file, double-billing, invoicing unapproved time, changing a sent invoice, overrunning a purchase order, the rate in force on a given day, and every column of the burn-down at each stage. The audit trail is tested by writing straight past the application — a raw insert is recorded exactly like one made through the API — and the lock is tested from both sides, through the application and by direct SQL.

Not proven. No live call to the Claude API was made. There was no credential in the environment this was built in, so the agent loop was exercised against a scripted stand-in for the API client. The request shape is asserted against the documented parameters — model, adaptive thinking, effort, tool schemas — but the round trip has not been run. Add a key and send one message. If it answers, the loop is good; if it does not, the error will be in the trace.

Who it is for. Six audiences want different things from this data, and several of them should not see all of it: recruiting, sales, back office, management, the customer, and the consultant. Two of those are the active focus — recruiting and sales. The back office is built to a working baseline and parked. Management, customer and consultant views are not started, and no screen is half-built for them.

Nobody signs in yet. The workspace picks an acting user from a list, and a client manager's approval is recorded against a typed name rather than an authenticated identity. That is fine while the only users are us. It is the gate for the customer and consultant viewpoints, because a client approving time and a consultant entering their week are people outside the company touching the same database — that needs authentication and a narrowed surface, not a filter over the internal app. Internal role visibility is the cheap half and can be layered on later: the model already carries ownership on accounts, candidates and projects, and every write is attributed.

Still to build in the two active areas. Submissions and pipeline stages have a schema but little product around them. There is no resume parsing into a contact record, no search worth the name across contacts and documents, and activity is a single note type where recruiters need call outcomes and follow-up dates.

Parked in the back office. Managed-service deliverables and milestones. Engagements with a team lead over several resources. The bench knowledge base and redeployment. Change orders exist as a table with no workflow around them — which matters, because the PO overrun guard tells you to raise one and then leaves you to do it by hand.
